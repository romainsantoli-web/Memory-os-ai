# Evaluation protocol 1.0 — frozen comparisons

Effective 2026-10-09. This protocol governs new final comparisons. Existing
`RESULTS.md` rows remain exploratory historical observations; they are not
retroactively held-out experiments.

## Questions and claims

Define each task before collecting results. Report three independent families:

| Family | Unit and primary score | Additional measures |
|---|---|---|
| Evidence retrieval | Question; Recall@k, fixed k | MRR, nDCG@k, macro by category and micro by question |
| Response quality | Question plus generated answer; answer accuracy | Groundedness, abstention accuracy, judge agreement |
| Agent task | Whole episode/task; objective success | Constraint violations, tool calls, time and cost |

Retrieval recall does not imply correct answers or successful agent tasks.
Report a family as **not evaluated** if no experiment was run for it. Specify
binary/graded relevance, empty-evidence handling, abstention and exact scoring
rules. Never merge these families into one headline percentage.

## Development and held-out test

Create a versioned split manifest from stable sample IDs. Group all questions
from the same conversation together. When user identity is available, group
by user as well; agent/repository tasks also group by repository. No identity
may occur in both development and test, even under different question IDs.
Use `group_keys` to declare all available identity dimensions and document
unavailable identities. The preflight checks disjointness for each declared
key; source adapters must verify split IDs exist in the dataset and that all
known identity keys have been supplied.

Use development data only to choose models, fusion weights, prompts, retrieval
budgets, enrichment, reranking and competitors. Freeze before looking at test
scores. Run the held-out test once per declared seed/repetition. Any retuning
creates a new campaign with a new untouched test set; retain failed runs and
explain exclusions. Gold answers/evidence/category labels are scorer-only
inputs and must never enter enrichment, query plans or reranker prompts.
Previously tuned LoCoMo conversations cannot become a pristine held-out test
simply by placing their questions into a new file.

## Datasets and competitors

Record dataset source, exact revision, local SHA-256, subset, sample counts,
category exclusions and license/usage provenance. Keep large/private data out
of Git; hash the actual local input. Include BM25, dense-only and production
v3/v4 baselines where applicable, plus chosen competitors with exact code
revisions. Publish all resolved configurations and executable commands,
including every disabled/enabled optional channel. Match budgets for each
system; any unavoidable mismatch must be an explicitly separate comparison.

Historical limits requiring explicit labels:

- The reported LoCoMo retrieval pilot contains 1,536 scored questions after
  adversarial/category-5 and empty-evidence exclusions. It is not full LoCoMo
  response accuracy, and excluding adversarial questions cannot establish
  abstention performance.
- The existing LongMemEval experiment is a stratified 150-question **oracle**
  sample with answer-containing turns, not full LongMemEval. Oracle context
  selection and real long-haystack retrieval are distinct settings.
- Offline candidate/ranking replay never performs search/model inference.
  Existing `latency_ms=0.0` values are placeholders, not measured speedups.

## Models, budgets and environment

For each enabled embedding, reranker, planner, response and judge model, record
ID, immutable revision/snapshot, provider, numerical precision, input format
and prompt SHA-256 (hash an empty prompt for roles with no prompt). Record
response sampling settings, tokenizer/revision, maximum sequence length,
truncation, batch size and any generated enrichments with file hashes in the
resolved system configuration. Disable unused roles explicitly.

Freeze shared limits for stored bytes, ingestion tokens, retrieval/context
and query tokens, model calls, wall time and paid API cost. A zero API budget
means no paid calls. Count offline enrichment/planning/reranking costs and
all initial indexing costs, not only the final query. Record CPU, GPU/MPS or
none, RAM, OS, Python, dependency lock and device. Record concurrency and
threads in configuration. Pin the candidate wheel/sdist SHA-256 and source
commit; changing either invalidates the freeze.

## Timing and statistics

Live timing includes ingestion, retrieval and generation separately and
end-to-end. Report cold and warm caches explicitly; predeclare warm-up queries
and repetition count. Include p50/p95, dispersion, context tokens (actual
specified tokenizer for final token-budget comparisons) and memory/disk
footprint. Synchronize accelerators before ending timed regions. Offline
replay timing must be marked unavailable for model/search latency; never
include zero placeholders in latency averages or speed comparisons.

Report per-category and total counts, macro and micro scores, paired deltas
against baselines and confidence intervals. Resample at conversation/user/
repository level, not independently by question within an identity group.
Freeze seeds, bootstrap repetitions and confidence level in resolved config.
Record failure/timeout rates and treat them under the predeclared scoring
rule; do not silently drop failed questions. Preserve per-question predictions,
scorer outputs and logs, including model/budget usage. Do not send private
memory contents to public logs or paid services without explicit authorization.

## Mandatory preflight and final report

Copy `manifest.template.json`, replace every `null` with a concrete value,
and create the referenced files. Relative paths are resolved from the manifest
folder. Split files have `dev` and `test` arrays, each containing rows such as
`{"id":"q1","conversation_id":"c1","user_id":"u1"}`. `test_count` is the
number of test sample rows. The template is deliberately incomplete and fails.

```bash
python v4/bench/evaluation_manifest.py campaign/manifest.json --freeze campaign/frozen.json
# Commit/archive the manifest, split files and lock before test execution.
python v4/bench/evaluation_manifest.py campaign/manifest.json --check-lock campaign/frozen.json
# Only after this check, execute the exact frozen per-system commands.
```

The validator rejects missing configuration, checksum changes, overlapping
identity groups, mixed metric families, floating model revisions and retuned
manifests. It refuses to overwrite a freeze file. This is a preflight checker,
not a benchmark runner: it does not execute shell commands, verify competitor
implementation or establish a blind test on its own. Archive the lock timestamp
and test start timestamp in the final report, plus the manifest digest. Every
final run must run `--check-lock` immediately before its execution and attach
the successful preflight log; exploratory legacy runner calls remain permitted
but cannot be labeled final qualification.

Final reports include exact coverage/subsets, configurations, budgets/hardware,
separate task-family scores, uncertainty, live timing or unavailable labels,
failures and artifact hashes. A missing field or failed preflight means the
comparison is incomplete, not a final benchmark result.
