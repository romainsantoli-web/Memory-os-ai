# 4.0.1rc1 — production foundation candidate

This candidate addresses the first production-readiness incidents found in
4.0.0. It is not a declaration of production Alpha readiness or a leaderboard
result. Qualification results are recorded separately from this change log.

## Behavior changes

- Project-scoped operations keep deduplication, consolidation, forgetting,
  statistics and core blocks within their requested project. MCP operations
  resolve an omitted project to the configured default. Explicit all-project
  reads remain available through `project="*"`.
- Core blocks are project-scoped by default. `scope="global"` explicitly shares
  a block; a project's own block overrides a global block of the same name.
  Legacy blocks without scope load into the `default` project. Review their
  contents before moving them or making them global.
- Similar wording does not establish that a fact contradicts an older fact.
  Fact updates require explicit `replaces` IDs or an explicit single-valued
  property identity. Complementary, multi-valued and untyped facts coexist.
  Callers that relied on implicit cosine-based replacement must supply update
  metadata; otherwise old facts remain visible.
- A store has one active engine. A second incompatible engine fails clearly.
  Multiple MCP clients must use one shared HTTP server, or separate stores.
  Python callers should use `with MemoryV4(...) as memory:` or `close()`.
- Mutating MCP tools accept `request_id`. A completed same-payload retry returns
  its durable receipt; a conflicting reuse fails. An interrupted request can
  have partial effects and reports an uncertain outcome instead of being
  applied twice. This is not a transaction across JSONL mutations.
- Distribution carries LGPL-3.0-or-later with its GPL companion text. CI checks
  both engines, distributions and semantic retrieval with the default model.
- New final benchmark comparisons have a versioned protocol and manifest
  preflight. Existing exploratory scores retain their original limitations.

See `v4/docs/SINGLE_WRITER.md`, `docs/DISTRIBUTION.md`, and
`v4/bench/protocols/v1.md` for the detailed contracts.

## Safe upgrade and rollback

1. Stop every process using the store. Identify the configured v4 data directory
   from your configuration or status response; do not assume the legacy v3 path.
2. Copy the **whole directory**, including JSONL source files and all metadata,
   to a dated backup outside the active directory. Keep the 4.0.0 wheel and its
   dependency environment. A live file-by-file copy is not a coherent backup.
3. Install the candidate in a separate environment and first point it at a copy
   of the store. Check item IDs/counts, scoped retrieval, project blocks and a
   reopen. Do not run two engines against the same copy.
4. Configure shared HTTP for multiple clients, bound to loopback. Remote
   authentication and client authorization belong to the next Alpha milestone;
   this release does not turn project labels into access-control boundaries.
5. For rollback, stop the candidate, preserve its post-upgrade directory for
   inspection, restore the pre-upgrade full backup into a separate directory,
   and open that restored directory with the original 4.0.0 environment.
   Changes made after the backup are not in the restored copy. Do not point
   4.0.0 directly at a store written by the candidate: it does not understand
   project-scoped blocks and the new fact update semantics.

The source repository provides a synthetic exercise:

```bash
python tools/qualify_v4_upgrade.py \
  --baseline-pythonpath /path/to/extracted-4.0.0-wheel \
  --candidate-pythonpath /path/to/extracted-candidate-wheel
```

It checks preservation of original items, conservative block migration,
typed updates, reopening and byte-identical restoration before reopening in
4.0.0. It uses temporary stores and the hash embedder; it is separate from
real-model, clean-install and platform-matrix qualification.

## Release gates

Publish a stable corrective release only after the CI matrix and distribution
checks pass for the exact source revision, candidate artifacts are verified,
and known blockers are resolved. Keep artifact hashes with the qualification
record. Never substitute a fresh, untested build for a qualified artifact.

Transaction-safe storage, physical purge, remote authentication, source
authority, user onboarding and the Alpha pilot remain subsequent tasks.
